# Claude Configuration for team-alpha-infra

## Project Context

This is the Infrastructure-as-Code repository for Team Alpha's AWS deployment. It uses Terraform to provision a three-tier architecture (web, app, data) on AWS, using external modules from the `pro-digital-uk` GitHub organization.

**Key Details:**
- Primary region: `eu-west-2`
- Default project name: `mupando`
- Backend: S3 (state is remote)
- Modules sourced from: `git@github.com:pro-digital-uk/<module-name>.git`

## How to Work with This Repository

### Terraform Operations

When making changes to Terraform:
1. Always run `terraform init` first if `.terraform/` has been removed
2. Run `terraform plan` to verify changes before applying
3. Use `terraform fmt` to maintain consistent formatting
4. Commit `.terraform.lock.hcl` (it ensures reproducible deployments)

### Variable and State Management

- Variables are defined in `variables.tf` with sensible defaults
- Create `terraform.tfvars` locally for environment-specific overrides (never commit this)
- Use `terraform.tfvars.example` as a template
- State is stored remotely in S3 — never commit `*.tfstate` files

### Module Configuration

External modules are sourced from GitHub using SSH URLs. If modules fail to download:
- Verify SSH keys are configured for GitHub
- Check that the pro-digital-uk organization modules exist and are accessible
- Module versions are pinned via `.terraform.lock.hcl`

### Common Issues and Fixes

**Recursive Module References**: If you see errors about deeply nested module paths (vpc.vpc.vpc...), the module source is likely pointing to itself. Module sources should reference external repositories, not the current repository.

**Missing Module Outputs**: When referencing module outputs (e.g., `module.vpc.vpc_id`), verify the output exists in the module. Use variables (`var.*`) for values not exposed as module outputs.

**Security Group and Variable Types**: Ensure type correctness when passing values to modules:
- `security_group_ids` must be a list (wrap single values like `[aws_security_group.web.id]`)
- Module variables must match their declared types

## Development Guidelines

- Document configuration decisions in commit messages
- Test changes with `terraform plan` before committing
- Keep variable defaults sensible for a dev environment
- Use descriptive names for resources and modules
- Add comments for non-obvious configurations

## File Organization

```
main.tf          — Module instantiation and primary resources
sg.tf            — Security group definitions
variables.tf     — Input variable declarations
outputs.tf       — Output value definitions
providers.tf     — AWS provider setup
backend.tf       — S3 state backend configuration
user_data/       — EC2 initialization scripts
```

## Team Preferences

- Prefer inline resource definitions over separate module files for simple resources
- Use local variables (`locals`) to consolidate repeated values
- Keep security groups in a separate file for clarity
- Always include descriptions in variables and outputs

## Useful Commands

```bash
# Initialize/reinitialize Terraform
terraform init

# Format code
terraform fmt -recursive

# Validate syntax
terraform validate

# Plan changes
terraform plan

# Apply changes
terraform apply

# Destroy infrastructure
terraform destroy

# Lock module/provider versions
terraform lock
```

## When to Ask for Help

- Integration with new AWS services
